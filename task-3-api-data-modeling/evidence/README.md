# Evidence Index

Every file in this directory is **generated from the live database** by a script in this repository. Nothing here is hand-written, paraphrased, or edited after capture. Each file can be regenerated with the command shown below.

| File | Generated by | What it proves |
|---|---|---|
| [`ddl-inventory.txt`](ddl-inventory.txt) | `npm run migrate` | Every constraint, index, and trigger that actually exists, queried from `pg_constraint`, `pg_indexes`, and `pg_trigger`. |
| [`query-plans.txt`](query-plans.txt) | `npm run explain` | 11 verbatim `EXPLAIN (ANALYZE, BUFFERS)` plans for the hot query patterns, plus the live index inventory. |
| [`constraint-violations.txt`](constraint-violations.txt) | `npm test` | Verbatim PostgreSQL error text for every constraint rejection the suite provokes. |

## ddl-inventory.txt

Query the catalog directly rather than transcribing a schema file, so the document cannot drift from the deployment. Any constraint or index name quoted in `HARD_QUESTIONS.md`, `ENTITIES.md`, `API_CONTRACTS.md`, or `REQUIREMENTS.md` should be greppable in this file.

Captured: 89 constraints, 28 indexes, 1 trigger.

## query-plans.txt

Eleven plans, each labelled with the endpoint it serves and the index the documentation claims serves it. Where the planner chose something else, the `VERDICT` line says so.

**All 11 plans chose `Seq Scan`,** because every table holds 5 rows. That is the right plan at that scale. The file additionally captures each query with `enable_seqscan = off` in a transaction-local setting, under a clearly marked `DIAGNOSTIC` heading, to demonstrate the index is reachable and correctly shaped. Those are reachability demonstrations, not performance results.

## constraint-violations.txt

One block per rejection, each containing the attempted SQL, the Prisma code, the PostgreSQL SQLSTATE, the constraint name where the server reported one, and the server's exact message.

The proofs are written so that a rejection by some *unrelated* constraint would still fail the test — each asserts the SQLSTATE and the specific object named in the server's response.

### One thing to read carefully

For the three partial unique indexes, PostgreSQL **does not report the index name**. The server returns only the conflicting key columns:

```
Key ("riderId")=(...) already exists.
```

So those proofs assert the SQLSTATE plus the conflicting column, and then prove the index identity behaviourally: **the same insert succeeds once the row's status leaves the partial predicate.** A blanket `UNIQUE` constraint would have failed that control, so the test distinguishes the two cases rather than trusting the error text.

The `check_review_completed_trip_only` name in these proofs is a **logical** identifier, not a `pg_constraint` entry — a CHECK constraint cannot read another table, so the rule is carried by `trg_review_completed_trip_only` and the trigger raises SQLSTATE `23514` with that token as the first word of its message. The real catalog objects are the trigger and its function `fn_review_completed_trip_only`, both listed in `ddl-inventory.txt`.

## Regenerating

```bash
npm run migrate   # rewrites ddl-inventory.txt
npm test          # rewrites constraint-violations.txt
npm run explain   # rewrites query-plans.txt
```

`npm test` needs the seed data present (`npm run seed`) and truncates `constraint-violations.txt` at the start of each run, so the file always reflects exactly one run.

The database is a managed free-tier instance that suspends when idle. If a run reports `Can't reach database server`, the instance is asleep — wait roughly a minute and retry.
