# PRD: E-Commerce Catalog & Ordering API — Bootcamp Task 1
**Status:** Implementation-ready — hand directly to Antigravity
**Version:** 1.0
**Owner:** Olaflay

> This PRD is the implementation contract. Where the original brief said "handle sensibly," this document makes the decision explicit so nothing is left to runtime improvisation. Every edge case below was chosen because it is either (a) explicitly required by the brief, (b) a common bootcamp-grading trap, or (c) a real production failure mode that would embarrass the project during defence or under a live demo.

---

## 1. Executive Summary

**What:** A public REST API modeling a small e-commerce business (categories, products, customers, orders), backed by PostgreSQL/Prisma, seeded with realistic Faker data, deployed publicly, with a minimal React consumer proving external usability.

**Why:** Task 1 requires demonstrating the ability to design, build, secure, document, and ship a real multi-resource API — not a CRUD toy. Grading rewards correctness under adversarial/edge-case input, not feature count.

**Who consumes it:** (a) the bootcamp grader, hitting the live URL directly and via curl; (b) the minimal consumer app; (c) hypothetically, any third-party developer — the README must satisfy a stranger with zero context.

**Success looks like:** every endpoint behaves correctly on the happy path AND on the specified edge cases, the seed is idempotent, the rate limiter is provably configured (not hardcoded), the consumer only ever talks to the deployed URL, and a grader can reproduce every claim from the README alone.

**Explicitly out of scope:** auth, payments, admin UI, GraphQL, real-time features, microservices, advanced analytics — see Section 2.

## 2. Scope

### In scope
Everything in Sections 3–21 of this document. Full CRUD-appropriate lifecycle for Orders; read-only for Products/Categories/Customers.

### Explicitly out of scope (non-goals)
- User authentication / authorization (no login, no JWT, no API keys for end users)
- Admin dashboard
- Marketing landing page
- Payments or real payment processing (orders are recorded, never paid)
- Complex/polished frontend (consumer is deliberately minimal)
- Mobile application
- GraphQL
- WebSockets / real-time updates
- Microservices / message queues / Redis / Docker / Kubernetes
- Multi-currency support (single currency: NGN, minor unit: kobo — see Section 4)
- Advanced analytics, reporting, or admin-facing dashboards
- Soft-delete recovery UI, audit-log UI
- Internationalization / localization
- Anything not required to demonstrate the API

**Why this list matters:** every item here is a plausible scope-creep trap. Antigravity must treat this list as a hard boundary, not a suggestion.

## 3. Functional Requirements

### Products
- List products (paginated, filterable, sortable)
- Get one product by ID
- Filter by `categoryId`, `minPrice`, `maxPrice`, `inStock`
- Sort by whitelisted fields only
- Products are read-only via the API (no create/update/delete endpoints — they exist only via seed). **Edge case:** if a grader tries `POST /api/v1/products`, the correct response is `404 Route not found` or `405 Method Not Allowed` on that path — not a silent 200. Decision: return `404` with a standard error envelope, since Express will not match the route at all; document this explicitly in the README so it isn't mistaken for a bug.

### Categories
- List categories (paginated)
- Get one category by ID
- Get products belonging to a category (paginated, filterable, sortable — reuses the product list logic with an implicit `categoryId` filter)
- **Edge case:** `GET /api/v1/categories/:id/products` for a category with zero products returns `200` with `"data": []` and `"meta": {"total": 0, "hasMore": false}` — never a 404. A 404 is reserved for a category that doesn't exist.

### Customers
- List customers (paginated, minimal fields only)
- Get one customer by ID
- No create/update/delete via API — customers exist only via seed, since customer creation would imply a registration flow that's out of scope
- **Edge case / privacy decision:** list/detail responses omit `phone` in the collection view and include it only in the single-resource view, to demonstrate deliberate data minimization (see Section 21). This is a design choice to document in defence prep, not a brief requirement — flag it as such.

### Orders
- Create an order (`POST`) — see full edge-case treatment in Section 6 and Section 22
- Retrieve an order (`GET`)
- Partially update an order (`PATCH`) — status transitions only, governed by a state machine (Section 6)
- Delete an order (`DELETE`) — allowed only while status is `pending`; otherwise `409 Conflict`

## 4. Data Model

**Global rules:**
- All identifiers are UUIDv4, generated by the database (`gen_random_uuid()` via Prisma `@default(uuid())` or the `pgcrypto` extension). **Security reason:** sequential integer IDs leak business volume (competitors can infer order count by watching ID growth) and enable trivial enumeration attacks (`/orders/1001`, `/orders/1002`, ...). UUIDs make enumeration computationally infeasible even with no auth in place — this is a meaningful compensating control given that authentication is explicitly out of scope.
- All money fields are stored as **integers in minor units** (kobo). `NGN 12,500.00` is stored as `1250000`. **Why:** floating-point decimals (`FLOAT`/`DOUBLE`) cannot represent currency exactly (`0.1 + 0.2 !== 0.3` in IEEE 754), which silently corrupts totals after enough operations. Integers in minor units eliminate rounding drift entirely. The API always returns money as integers; the consumer app is responsible for formatting (`amount / 100`) for display. Document this loudly in the README's Design Decisions section — it's a common defence question.
- All timestamps are stored in UTC (`timestamptz` in Postgres) and returned as ISO-8601 strings. **Edge case:** never store `timestamp without time zone` — it silently assumes server-local time and causes off-by-hours bugs the moment the deploy region or a client's timezone differs.
- Single currency only: every `currency` field is fixed to `"NGN"` and validated as such on input. This is a deliberate simplification — if a client ever sends a different currency code, reject with `422`. Document why (avoids exchange-rate complexity, which is explicitly out of scope).

### Customer
| Field | Type | Required | Default | Validation | Unique | Indexed | Description |
|---|---|---|---|---|---|---|---|
| id | UUID | yes | `gen_random_uuid()` | v4 format | yes (PK) | yes (PK) | Primary key |
| name | string | yes | — | 2–100 chars, trimmed | no | no | Full name |
| email | string | yes | — | RFC 5322 format, lowercased before storage | **yes** | yes | Contact email |
| phone | string | no | null | E.164-ish loose regex, max 20 chars | no | no | Contact phone |
| createdAt | datetime | yes | `now()` | — | no | yes (for sort/pagination stability) | Creation time |
| updatedAt | datetime | yes | `now()`, auto-update | — | no | no | Last update time |

**Edge case — email uniqueness:** enforce case-insensitivity by lowercasing on write AND using a citext/lowercase unique index, otherwise `Alice@x.com` and `alice@x.com` are treated as different customers by Postgres's default case-sensitive unique constraint — a classic hidden bug.

### Category
| Field | Type | Required | Default | Validation | Unique | Indexed | Description |
|---|---|---|---|---|---|---|---|
| id | UUID | yes | `gen_random_uuid()` | v4 | yes (PK) | yes | Primary key |
| name | string | yes | — | 2–60 chars, trimmed | yes | yes | Category name |
| description | string | no | null | max 500 chars | no | no | Short description |
| createdAt | datetime | yes | `now()` | — | no | no | — |
| updatedAt | datetime | yes | `now()`, auto-update | — | no | no | — |

### Product
| Field | Type | Required | Default | Validation | Unique | Indexed | Description |
|---|---|---|---|---|---|---|---|
| id | UUID | yes | `gen_random_uuid()` | v4 | yes (PK) | yes | Primary key |
| categoryId | UUID | yes | — | must reference existing category | no | **yes (FK)** | Owning category |
| name | string | yes | — | 2–150 chars | no | yes (used by future search; not required now, documented as a "why not" if omitted) | Product name |
| description | string | no | null | max 2000 chars | no | no | — |
| price | integer | yes | — | > 0, minor units (kobo) | no | **yes** (used by min/max price filter and sort) | Unit price in kobo |
| currency | string | yes | `"NGN"` | must equal `"NGN"` | no | no | ISO 4217 code, fixed |
| stockQuantity | integer | yes | 0 | >= 0 | no | no (filtered via boolean `inStock`, not raw value, so not indexed directly — see Section 9) | Units in stock |
| createdAt | datetime | yes | `now()` | — | no | no | — |
| updatedAt | datetime | yes | `now()`, auto-update | — | no | no | — |

**Edge case — negative/zero stock:** `stockQuantity` has a Postgres `CHECK (stockQuantity >= 0)` constraint in addition to app-level validation, so a bug in the order-fulfilment code path cannot push stock negative even under a race condition (defense in depth — the DB is the last line, not just the app).

### Order
| Field | Type | Required | Default | Validation | Unique | Indexed | Description |
|---|---|---|---|---|---|---|---|
| id | UUID | yes | `gen_random_uuid()` | v4 | yes (PK) | yes | Primary key |
| customerId | UUID | yes | — | must reference existing customer | no | **yes (FK)** | Owning customer |
| status | enum | yes | `"pending"` | one of: `pending`, `paid`, `shipped`, `delivered`, `cancelled` | no | yes | Order lifecycle state |
| totalAmount | integer | yes | computed server-side | >= 0, minor units | no | no | Sum of line items, **never trusted from client** |
| currency | string | yes | `"NGN"` | must equal `"NGN"` | no | no | — |
| createdAt | datetime | yes | `now()` | — | no | yes (default sort) | — |
| updatedAt | datetime | yes | `now()`, auto-update | — | no | no | — |

**Critical edge case — totalAmount integrity:** the client never supplies `totalAmount`. The server always recomputes it from the OrderItems it creates, using the *current* product price at order time. This closes an obvious price-tampering vector (a client sending `{"totalAmount": 1}` for a real order) that a naive implementation would miss.

### OrderItem
| Field | Type | Required | Default | Validation | Unique | Indexed | Description |
|---|---|---|---|---|---|---|---|
| id | UUID | yes | `gen_random_uuid()` | v4 | yes (PK) | yes | Primary key |
| orderId | UUID | yes | — | must reference existing order | no | **yes (FK)** | Parent order |
| productId | UUID | yes | — | must reference existing product | no | **yes (FK)** | Referenced product |
| quantity | integer | yes | — | >= 1, integer | no | no | Units ordered |
| unitPrice | integer | yes | — | > 0, minor units, **snapshotted from Product.price at order time** | no | no | Price at time of purchase |
| createdAt | datetime | yes | `now()` | — | no | no | — |

**Critical edge case — price snapshotting:** `unitPrice` is copied from the product at the moment the order is created and is never recalculated. If the product's price changes next week, past orders' totals must not silently change. This is the single most commonly missed requirement in bootcamp e-commerce projects and is worth calling out explicitly in the README's Design Decisions section.

**Edge case — deleting a product referenced by historical orders:** since products are seed-only and never deleted via the API in this scope, hard-delete cascading is not exercised in practice, but the schema must still define the FK behavior defensively: `Product` → `OrderItem` uses `onDelete: Restrict` (not `Cascade`), so a stray manual deletion can never silently erase order history. Same for `Customer` → `Order` (`Restrict`). `Category` → `Product` uses `Restrict` as well — a category with products cannot be deleted (not exposed via API, but the constraint should exist at the DB level for correctness).

## 5. Relationship Model

- **Customer → Order**: one-to-many. FK `Order.customerId → Customer.id`, `onDelete: Restrict`.
- **Category → Product**: one-to-many. FK `Product.categoryId → Category.id`, `onDelete: Restrict`.
- **Order → OrderItem**: one-to-many. FK `OrderItem.orderId → Order.id`, `onDelete: Cascade` (deleting an order — while in `pending` status only, per Section 3 — should clean up its own line items; this is the one legitimate cascade in the schema).
- **Product → OrderItem**: one-to-many. FK `OrderItem.productId → Product.id`, `onDelete: Restrict`.
- **Order ↔ Product**: many-to-many, realized through `OrderItem`.

### Textual ERD
```
Customer (1) ──< (many) Order (1) ──< (many) OrderItem >── (many) (1) Product >── (many) (1) Category
```

### FK behavior summary
| Relationship | On delete | Reason |
|---|---|---|
| Order → Customer | Restrict | Never orphan financial history |
| Product → Category | Restrict | Never orphan a product's classification |
| OrderItem → Order | Cascade | Line items have no independent meaning without their order |
| OrderItem → Product | Restrict | Preserve historical integrity of what was purchased |

## 6. API Design

Base path for every route: `/api/v1/`

| Method | Path | Purpose | Auth | Params | Body | Validation | Success | Errors |
|---|---|---|---|---|---|---|---|---|
| GET | `/products` | List products | none | `limit, offset, sort, order, categoryId, minPrice, maxPrice, inStock` | — | see §8–§10 | 200 | 400 |
| GET | `/products/:id` | Get one product | none | `:id` UUID | — | `:id` must be valid UUID format | 200 | 400 (malformed UUID), 404 (valid UUID, no match) |
| GET | `/categories` | List categories | none | `limit, offset` | — | see §8 | 200 | 400 |
| GET | `/categories/:id` | Get one category | none | `:id` UUID | — | same as products | 200 | 400, 404 |
| GET | `/categories/:id/products` | Products in a category | none | `:id`, plus all product list params | — | category must exist first, then product filters apply | 200 | 400, 404 (category not found) |
| GET | `/customers` | List customers | none | `limit, offset` | — | see §8 | 200 | 400 |
| GET | `/customers/:id` | Get one customer | none | `:id` UUID | — | — | 200 | 400, 404 |
| POST | `/orders` | Create an order | none | — | `{customerId, items: [{productId, quantity}]}` | see below | 201 | 400 (malformed body/JSON), 404 (customer/product not found), 409 (insufficient stock), 422 (validation) |
| GET | `/orders/:id` | Get an order (with items) | none | `:id` UUID | — | — | 200 | 400, 404 |
| PATCH | `/orders/:id` | Update order status | none | `:id` UUID | `{status}` | must be a valid, allowed transition | 200 | 400, 404, 409 (illegal transition), 422 |
| DELETE | `/orders/:id` | Delete a pending order | none | `:id` UUID | — | order must be `pending` | 204 | 400, 404, 409 (not pending) |

**Endpoint deviation from the brief, and why:** none of the listed endpoints were removed. The only addition is `GET /healthz` (Section 20) for deployment-platform health checks — a purely operational endpoint, not a product feature, so it doesn't violate the scope boundary.

### `POST /orders` — request contract
```json
{
  "customerId": "uuid",
  "items": [
    { "productId": "uuid", "quantity": 2 },
    { "productId": "uuid", "quantity": 1 }
  ]
}
```
**Validation and edge cases, in the order they're checked:**
1. Body must be valid JSON → malformed JSON returns `400` (this happens at the body-parser layer, before validation even runs).
2. `customerId` required, valid UUID format → else `422`.
3. `items` required, non-empty array → an empty array (`"items": []`) is `422`, not a silently-accepted zero-value order.
4. Each item needs `productId` (valid UUID) and `quantity` (integer >= 1) → else `422`, and the error response identifies which item index and field failed.
5. Duplicate `productId` within the same `items` array → **merge quantities** rather than creating two OrderItem rows for the same product (documented decision — the alternative, rejecting the whole order, is stricter but worse UX; either is defensible, but pick one and document it).
6. `customerId` doesn't reference an existing customer → `404`.
7. Any `productId` doesn't reference an existing product → `404`, naming the offending ID.
8. Any requested `quantity` exceeds that product's current `stockQuantity` → `409 Conflict` (not 422 — this is a business-state conflict, not a malformed request), naming the product and available quantity.
9. **Concurrency:** stock check-and-decrement happens inside a single database transaction using `SELECT ... FOR UPDATE` (row-level lock) or Prisma's interactive transaction with a re-read of stock inside the transaction, so two simultaneous orders for the last unit of a product cannot both succeed. Whichever request loses the race gets `409`.
10. On success: `totalAmount` is computed server-side as `Σ(unitPrice × quantity)` using each product's *current* price, `Order` and all `OrderItem` rows are created atomically, and product `stockQuantity` is decremented atomically in the same transaction. If any step fails, the entire transaction rolls back — no partial orders, no partial stock decrements.
11. **Idempotency (recommended, documented as a stretch addition, not required by the brief):** support an optional `Idempotency-Key` request header. If a request with the same key arrives again within a short window (e.g. 5 minutes), return the original response instead of creating a duplicate order. This protects against the extremely common failure mode of a client retrying a POST after a timeout, not realizing the first request actually succeeded. Implement with a small `IdempotencyKey` table or an in-memory cache with TTL — keep it simple, document the tradeoff (in-memory won't survive a restart; acceptable at this scale).

### `PATCH /orders/:id` — status state machine
Only `status` is mutable via PATCH. Allowed transitions:
```
pending   → paid, cancelled
paid      → shipped, cancelled
shipped   → delivered
delivered → (terminal, no further transitions)
cancelled → (terminal, no further transitions)
```
**Edge cases:**
- Requesting a transition not in this table (e.g. `pending → delivered`, or `delivered → pending`) → `409 Conflict` with a message naming the current status and the requested one.
- Requesting the same status the order already has → treat as a no-op success (`200`, unchanged resource) rather than an error — idempotent PATCH is good practice and costs nothing.
- Any other field in the PATCH body (`totalAmount`, `customerId`, etc.) is **ignored**, not erroring, per standard PATCH semantics — but document this choice, since some graders expect a `422` on unknown fields. Decision: ignore unknown/immutable fields silently for PATCH (idiomatic), but validate them strictly on POST.
- Cancelling a `paid` order does **not** restock inventory automatically in this scope (that's a "restock/refund" business process, arguably a stretch feature) — document this as an explicit non-goal so it isn't mistaken for an oversight.

### `DELETE /orders/:id`
- Only permitted while `status === "pending"`. Any other status → `409 Conflict`, "Cannot delete an order once it has progressed past pending state; use PATCH to cancel instead."
- Deleting a pending order cascades to its OrderItems (Section 5) but does **not** restock inventory, because a `pending` order never decremented stock in the first place — stock is only decremented at creation success, and a pending order already reflects that decrement having happened. **Correction/decision:** since stock is decremented at order creation regardless of status, deleting (not just cancelling) a pending order **should** restock, because the goods are being released back to inventory with no compensating "cancelled" record. Implement DELETE as: restock all associated OrderItem quantities, then hard-delete the order and its items. This is called out explicitly because it's an easy inconsistency to miss if cancellation and deletion aren't reasoned about together.
- Successful delete returns `204 No Content` with an empty body.

## 7. Response Contract

All responses use one of three envelope shapes. No endpoint deviates.

**Collections:**
```json
{ "data": [ /* array of resources */ ], "meta": { "total": 340, "limit": 20, "offset": 0, "hasMore": true } }
```

**Single resource:**
```json
{ "data": { /* resource object */ } }
```

**Errors:**
```json
{ "error": { "code": "NOT_FOUND", "message": "Product not found" } }
```

**Edge cases:**
- `DELETE` success returns `204 No Content` with **no body at all** (not even `{"data": null}`) — an empty envelope on a 204 is itself a spec violation many implementations get wrong.
- Validation errors (`422`) extend the error object with a `field` (and optionally `index` for array items):
  ```json
  { "error": { "code": "VALIDATION_ERROR", "message": "quantity must be at least 1", "field": "items[0].quantity" } }
  ```
- Error `code` values are a closed, documented enum: `BAD_REQUEST`, `NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`, `RATE_LIMITED`, `INTERNAL_ERROR`. A client should be able to `switch` on `code` without parsing `message` text.
- `message` is always human-readable English and never leaks internals (stack traces, SQL, file paths) — see Section 12 and 21.

## 8. Pagination

Offset pagination, chosen for implementation speed and conceptual clarity (see Section 27 for the defence answer on cursor vs offset).

- `limit`: default `20`, max `100`.
- `offset`: default `0`.
- Response `meta`: `{ total, limit, offset, hasMore }`, where `hasMore = offset + limit < total`.

| Input | Behavior |
|---|---|
| `limit` omitted | defaults to 20 |
| `limit` > 100 (e.g. 5000) | **clamped to 100**, not rejected — the request still succeeds, just capped |
| `limit = 0` | `400 Bad Request` — zero is not a meaningful page size and is more likely a client bug than an intentional "give me nothing" |
| `limit` negative | `400 Bad Request` |
| `limit` non-numeric (e.g. `?limit=abc`) | `400 Bad Request` |
| `offset` negative | `400 Bad Request` |
| `offset` beyond dataset (e.g. `offset=99999` on a 340-row table) | `200 OK` with `"data": []`, `"total": 340`, `"hasMore": false` — **not** an error; requesting a page past the end is a valid, well-defined empty result |
| `offset` non-numeric | `400 Bad Request` |

**Edge case — pagination drift under concurrent writes:** offset pagination can show a duplicate or skipped row if rows are inserted/deleted between page requests (a known, accepted limitation of offset pagination vs cursor pagination). Document this honestly in the README's Design Decisions section rather than pretending it doesn't exist — it's a strong, correct answer for the defence.

## 9. Filtering

Applies to `GET /products` and (with an implicit `categoryId`) `GET /categories/:id/products`.

| Param | Type | Validation | Behavior | Invalid input |
|---|---|---|---|---|
| `categoryId` | UUID | must be valid UUID format | exact match filter | malformed UUID → `400`; well-formed but non-existent category → `200` with empty results (not 404 — a filter that matches nothing is not an error) |
| `minPrice` | integer (kobo) | >= 0 | `price >= minPrice` | non-numeric or negative → `400` |
| `maxPrice` | integer (kobo) | >= 0 | `price <= maxPrice` | non-numeric or negative → `400` |
| `inStock` | boolean (`true`/`false`) | must be exactly `"true"` or `"false"` string | `true` → `stockQuantity > 0`; `false` → `stockQuantity = 0` | any other value (`"yes"`, `"1"`) → `400` |

**Edge cases:**
- `minPrice > maxPrice` (e.g. `minPrice=5000&maxPrice=1000`) → `400 Bad Request`, "minPrice cannot exceed maxPrice" — a naive implementation would silently return zero results instead of flagging the likely client error.
- Combining `categoryId` on the already-scoped `/categories/:id/products` route — if the query string also includes a *different* `categoryId` than the path param, the path param wins and the query param is ignored (documented, not an error).
- Unknown/unsupported query params (e.g. `?color=red`) are **ignored**, not errored — this keeps the API forward-compatible with clients that might send extra params, but is a deliberate choice worth documenting (the stricter alternative, `400` on unknown params, is equally defensible; pick one).

## 10. Sorting

Params: `sort` and `order`.

- Whitelisted sortable fields for products: `price`, `createdAt`, `name`, `stockQuantity`.
- Whitelisted sortable fields for categories/customers/orders: `createdAt`, `name` (categories/customers), `createdAt`, `status`, `totalAmount` (orders).
- `order` accepts `asc` or `desc` only, case-insensitive; default `asc`.
- Default sort (when `sort` is omitted): `createdAt desc` for all list endpoints — newest-first is the most useful default for a catalog/orders API.

**Edge cases:**
- Unknown `sort` field → `400 Bad Request`, "Unsupported sort field: X. Allowed: price, createdAt, name, stockQuantity" — never silently fall back to the default, per the brief.
- Unknown `order` value (e.g. `?order=upwards`) → `400 Bad Request`.
- `sort` provided without `order` → apply default `order=asc`.
- Multiple `sort` query params (e.g. `?sort=price&sort=name`, which Express parses as an array) → `400 Bad Request`, "Only one sort field is supported" — reject explicitly rather than silently taking the first or last value.
- Ties in sort order (e.g. two products with identical `createdAt`) → add a deterministic secondary sort key (`id asc`) under the hood so pagination is stable across requests; otherwise identical-timestamp rows can appear in a different relative order on page 2 than page 1, corrupting pagination silently.

## 11. Validation

Library: **Zod**, centralized in a `validation/` directory as one schema per resource/action (`createOrderSchema`, `productListQuerySchema`, etc.), imported into route middleware — never inline `if` checks scattered through controllers.

Layers validated: request body, query parameters, route parameters (`:id`).

**Edge cases:**
- Route param `:id` that isn't a valid UUID at all (e.g. `/products/abc`) → `400 Bad Request` ("Invalid ID format"), not `404` — a malformed ID is a client request error, distinct from a well-formed ID that simply doesn't match a record (`404`). This distinction is a common grading trap.
- Extra/unexpected fields in a request body (e.g. `POST /orders` with an unexpected `discountCode` field) → Zod's `.strict()` mode rejects unknown keys with `422`, preventing silent mass-assignment of fields that shouldn't be settable.
- Type coercion traps: query params arrive as strings always (`?limit=20` is the string `"20"`, not the number `20`). Every numeric/boolean query schema must explicitly coerce (`z.coerce.number()`) and then validate the *coerced* value — a common bug is validating the raw string and never converting it, so `limit` ends up being compared as a string downstream.
- Whitespace-only strings (e.g. `"name": "   "`) are treated as empty after `.trim()` and fail "required" validation — don't let a client send a technically-non-empty but meaningless string.
- Required-field failures return `422 Unprocessable Entity` and name the exact field (see Section 7's error shape).

## 12. Error Handling

| Status | When |
|---|---|
| 400 | Bad/malformed query params, invalid sort field, negative offset/limit, malformed UUID in route param, malformed JSON body, multiple values for a single-value param |
| 404 | Resource does not exist (well-formed ID, no match) or route doesn't exist |
| 409 | Legal-request-but-illegal-state conflicts: insufficient stock, illegal order status transition, deleting a non-pending order |
| 422 | Body fails schema validation (missing/invalid required fields, unknown fields in strict schemas) |
| 429 | Rate limit exceeded |
| 500 | Unexpected server failure |

**Centralized strategy:** a single Express error-handling middleware (registered last) catches everything — thrown validation errors, Prisma errors, and uncaught exceptions — and maps them to the correct status/envelope. Route handlers and services never write raw `res.status(500)` manually; they throw typed errors (`NotFoundError`, `ConflictError`, `ValidationError`) that the middleware translates.

**Edge cases:**
- A Prisma unique-constraint violation (e.g. a race on a unique email, if that path is ever exercised) is caught and mapped to `409`, not allowed to bubble up as an unhandled `500` with a raw Postgres error message.
- Uncaught exceptions in async route handlers must be wrapped (e.g. `express-async-errors` or manual `try/catch` + `next(err)`) — a classic Express bug is an unhandled promise rejection inside an `async` route handler that crashes the process instead of returning a `500`.
- In production, the 500 response body **never** includes the stack trace, the error message from the underlying library, or any internal path — only a generic `"Internal server error"` plus a `code`. Full details are logged server-side (with a request-correlation ID) for debugging, never sent to the client.
- Never return `200` with an `{"error": ...}` body baked into `data` — every error path must use the correct non-2xx HTTP status. This is explicitly called out because it's an extremely common shortcut under time pressure.

## 13. Rate Limiting

IP-based, default **100 requests/minute/IP**, response `429` with a `Retry-After` header (seconds until the window resets).

Configuration variables (documented in `.env.example`):
```
RATE_LIMIT_WINDOW_MS=60000
RATE_LIMIT_MAX_REQUESTS=100
```
Read via `process.env` in a single config module (`config/index.ts`), never hardcoded inside route files, so the limit can be tuned per environment (e.g. looser in a local dev `.env`, or tightened for the live grading window) without a code change.

**Edge cases:**
- **Trust proxy:** Render/Railway sit behind a load balancer/proxy, so `req.ip` is unreliable unless Express's `app.set('trust proxy', 1)` is configured — otherwise every request appears to come from the proxy's IP, and the entire deployment shares a single rate-limit bucket, locking out all users simultaneously the moment traffic exceeds 100/min in aggregate. This is one of the most common "rate limiting works locally but is broken in production" bugs — call it out explicitly in the verification plan (Section 24).
- The rate limiter must run **before** heavy work (route handlers, DB queries) so an attacker sending a flood of requests doesn't get to consume database connections before being limited.
- Health-check requests (Section 20) from the hosting platform's own uptime monitor should be excluded from the limit (or given a very high separate limit), otherwise the platform's own keep-alive pings can exhaust the quota and lock out real users — document whichever choice is made (excluding `/healthz` from limiting is the simpler, recommended default).
- 429 responses still use the standard error envelope (`{"error": {"code": "RATE_LIMITED", "message": "..."}}`) plus the `Retry-After` header — don't return a bare-text 429.

## 14. Database

PostgreSQL + Prisma. Full schema lives in `prisma/schema.prisma`.

**Indexes (only where they serve an actual query — not on every column):**
- `Customer.email` — unique index, used by the (documented but unexposed) uniqueness constraint.
- `Product.categoryId` — FK index, used by category→products lookups and the `categoryId` filter.
- `Product.price` — used by `minPrice`/`maxPrice` filters and `sort=price`.
- `Order.customerId` — FK index (not exposed as a filter in this scope, but correct FK hygiene).
- `Order.status` — used if/when status filtering is added later; included now since it's cheap and status is a low-cardinality field that benefits from indexing for future filtering.
- `Order.createdAt` — default sort field.
- `OrderItem.orderId`, `OrderItem.productId` — FK indexes, used when loading an order's items and when checking product usage.

**Deliberately not indexed:** `Product.description`, `Product.stockQuantity` (filtered via a boolean-style `inStock` derived condition rather than a raw numeric range, so a plain index gives little benefit at this data volume), `Customer.name`/`phone` — none of these are queried by exact-match or range filters in this scope, so an index would only add write overhead with no read benefit.

**Check constraints:**
- `Product.stockQuantity >= 0`
- `Product.price > 0`
- `OrderItem.quantity >= 1`
- `OrderItem.unitPrice > 0`

**Edge cases:**
- **Connection pooling:** serverless/managed Postgres on Render/Railway has a hard connection cap. Prisma's default pool size can exhaust this under even light concurrent load. Set `connection_limit` explicitly in the `DATABASE_URL` (e.g. `?connection_limit=5`) sized to the platform's plan, and document why in the README — "it worked with 1 request but failed under the grader's curl loop" is a real, avoidable failure mode.
- **Migrations in production:** use `prisma migrate deploy` (not `migrate dev`) as part of the deploy step — `migrate dev` can prompt interactively or reset data, which must never happen against production.
- All money/quantity columns use `Int` (Prisma) mapped to Postgres `integer`, sufficient for kobo amounts at this scale (max ~21.4M NGN before overflow, more than adequate for a bootcamp demo — call this bound out explicitly rather than leaving it implicit).

## 15. Seeding

Faker.js, run via `npm run seed` → `prisma/seed.ts`, wired into `package.json`'s `prisma.seed` field so `prisma db seed` also works.

**Target volumes:**
- Categories: 40
- Products: 400 (evenly-ish distributed across categories via weighted random assignment, not a strict even split — real catalogs aren't uniform)
- Customers: 400
- Orders: 800
- OrderItems: 1–5 per order (randomized), giving roughly 2,000–3,000 line items total

**Idempotency strategy:** the seed script starts by truncating all four tables in FK-safe order (`OrderItem → Order → Product/Customer → Category`, using `TRUNCATE ... CASCADE` or ordered `deleteMany()` calls) before regenerating — this is simpler and more reliable than trying to `upsert` against Faker's inherently non-deterministic values. Running `npm run seed` twice produces a fresh, consistent dataset of the same target size, never duplicate or ever-growing data. Document explicitly: **this seed is destructive by design** — it is not meant to be run against a database with real user-generated data, which is a non-issue here since there is no user-generated data path in scope.

**Edge cases:**
- Faker is seeded with a fixed `faker.seed(42)` call at the top of the script so the *shape* of generated data (not identical values, but statistical distribution and reproducible edge cases like some out-of-stock products) is consistent across environments for easier debugging and grading reproducibility.
- Ensure at least a handful of products have `stockQuantity: 0` deliberately (not just whatever Faker's random range happens to produce) so the `inStock=false` filter and the out-of-stock order-creation `409` path are always exercisable in testing/demo, not dependent on random luck.
- Ensure order `status` values are deliberately distributed across all five states (not just random, but guaranteed at least N orders in each status) so every PATCH/DELETE edge case in Section 6 is demonstrable against seeded data without manual setup.
- The seed script is committed to Git (`prisma/seed.ts`); the generated `.sql` dump or database file is never committed.

## 17. Minimal Consumer Application

Vite + React, calling the deployed API URL only (injected via `VITE_API_BASE_URL` env var at build time — never hardcoded, never `localhost`).

Features: product list, one filter (`inStock` toggle or `categoryId` dropdown), pagination via a "Next Page" button, loading state, empty state, error state.

**Edge cases:**
- **Cold start:** Render's free tier spins down idle services; the first request after inactivity can take 10–30+ seconds. The consumer must show a distinct "waking up the API, this may take a moment" loading message (not just a generic spinner that looks frozen) so a grader doesn't assume the app is broken.
- **429 handling:** if the consumer itself gets rate-limited (e.g. from rapid clicking), it shows the actual error message from the API's error envelope, not a generic "something went wrong."
- **Stale request race:** rapid double-clicks on "Next Page" must not let an earlier, slower response overwrite a later page's state — use an `AbortController` per request or a simple request-sequence-number guard.
- **Next Page at end of data:** disable the button when `meta.hasMore === false`, rather than letting the user page into an empty result and wonder if something broke.
- Build-time vs runtime env var handling: Vite bakes `VITE_*` vars in at build time, so the deployed API URL must be set correctly in the frontend hosting platform's build environment, not just a local `.env` — a very common "works locally, breaks in prod" mistake for Vite specifically (unlike a Node server, there's no runtime `process.env` to fall back on after the bundle is built).

## 27. Defence Preparation

**Why offset pagination?** It's simpler to implement and reason about — `LIMIT`/`OFFSET` map directly to a mental model of "pages," and it's sufficient for a catalog that isn't experiencing constant high-frequency writes.

**When would cursor pagination be better?** When the underlying data changes frequently between page loads (e.g. a live social feed) — cursor pagination anchors to a specific row (`"give me everything after this ID/timestamp"`) so it doesn't skip or duplicate rows when items are inserted or deleted mid-scroll, unlike offset pagination.

**What happens if someone requests page 50 when only 30 pages exist?** The API returns `200` with an empty `data` array and `hasMore: false` — an out-of-range page is a valid, well-defined empty result, not an error, because the client didn't do anything wrong; the data just isn't there.

**Where is the rate limit configured?** In environment variables (`RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_MAX_REQUESTS`), read once at startup into a config module — never a hardcoded number inside a route file.

**Why configured rather than hardcoded?** So the limit can be tuned per environment (looser locally, tuned for a demo/grading window) without touching or redeploying code, and so the value is auditable in one place.

**How could you add a field without breaking existing clients?** Add it as an optional field with a sensible default in both the schema and the response — existing clients that don't know about it simply ignore the extra key (this is why the response envelope is a flat, additive object rather than a rigid positional structure). Never repurpose or remove an existing field name; deprecate and version instead if a breaking change is ever truly necessary.

**Why generated identifiers (UUIDs)?** Sequential integer IDs leak information (total record count, growth rate over time) and make it trivial to enumerate every resource by incrementing a counter — a real risk in an API with no authentication. UUIDs make that enumeration computationally infeasible.

**Added — why is totalAmount always server-computed?** Because trusting a client-supplied price or total on a financial record is a direct, well-known fraud vector; the server is the only party that can be trusted to state what something actually costs.

**Added — why snapshot unitPrice per order line instead of joining live to the product's current price?** Because an order is a historical record of what was agreed at purchase time — if the product's price later changes, past orders must not retroactively change with it. This is the same reasoning any real invoicing/accounting system uses.

## Decision Log

| # | Decision | Alternative considered | Why this one |
|---|---|---|---|
| 1 | Offset pagination | Cursor pagination | Faster to implement correctly, sufficient for read-heavy catalog data at this scale |
| 2 | Money as integer minor units | Decimal/Numeric Postgres type | Simpler arithmetic in application code, matches how most payment APIs (Stripe, Paystack) represent amounts |
| 3 | UUIDs over sequential IDs | Sequential integers | Enumeration resistance given no auth layer exists |
| 4 | DELETE restocks inventory | DELETE does not restock (only cancellation restocks) | A deleted pending order releases its reserved stock; leaving stock decremented for a deleted order would silently shrink available inventory forever |
| 5 | Server-computed totalAmount, price snapshot per line item | Trust client-supplied total; live-join to current product price | Prevents price tampering and preserves historical order accuracy |
| 6 | Seed is destructive (truncate + regenerate) | Idempotent upsert against fixed keys | Faker's random data doesn't have natural stable keys to upsert against; truncate-and-regenerate is simpler and equally repeatable given there's no real user data to preserve |
| 7 | Unknown query params ignored; unknown body fields rejected (422) | Reject both, or accept both | Query params are commonly extended by clients harmlessly; a POST body directly creates a financial record, so unexpected fields there are a stronger signal of a bug or tampering attempt |
| 8 | FK deletes default to `Restrict` except `OrderItem→Order` (`Cascade`) | Cascade everywhere | Preserve financial/historical integrity by default; only cascade where the child record has no independent meaning |
